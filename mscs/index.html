MSC Support

MSCs (Matrix Spec Changes) are proposals to extend or modify the Matrix protocol. This page tracks the implementation status of notable MSCs in Zendrite.

Many MSCs listed here have since been merged into the Matrix specification proper. They are listed by their original MSC number and the first spec version which includes them. Feature support does not imply support for an entire specification version; see the client API conformance audit for discovery policy and remaining blockers.

The unstable org.matrix.msc4222.use_state_after parameter is answered with org.matrix.msc4222.state_after. See state after the timeline

Sticky events

Section titled “Sticky events”

/versions advertises org.matrix.msc4354 in unstable_features, which Element Call needs before it sends call memberships as sticky events. PUT /_matrix/client/v3/rooms/{roomId}/send/{eventType}/{txnId} accepts org.matrix.msc4354.sticky_duration_ms and puts it into the event as msc4354_sticky.duration_ms. As in Synapse, the duration must be a non-negative integer, otherwise the request fails with 400 M_INVALID_PARAM, and durations above an hour are kept in the event but count as one hour. The parameter is ignored when sending state events.

An event stays sticky from the earlier of its origin_server_ts and the time Zendrite received it, for its duration of at most an hour. Redacting an event removes its stickiness. While an event is sticky, /sync delivers it in a msc4354_sticky.events section of its joined room, unless the timeline of the same response carries it after the timeline filter. Each sticky event is delivered once as the client’s sync position advances, at most 100 per response, and joining a room delivers all of the room’s sticky events at once. Sticky events of ignored users are left out, and with lazy-loaded members their senders’ memberships are included. Sticky events in the sticky section and in timelines carry unsigned.msc4354_sticky_duration_ttl_ms, the milliseconds until they expire.

Sliding sync delivers sticky events through the org.matrix.msc4354.sticky_events extension, for every joined room the lists or room subscriptions match, also outside the lists’ windows. The extension takes since and limit (default 100), and answers with rooms and next_batch, or is left out when there is nothing to deliver. Sticky events in the timelines of the response are left out of the extension and carry their TTL in the timeline instead, when the extension is enabled.

History visibility does not hide sticky events from joined users, in /sync, sliding sync, /messages, /context, /event and the other endpoints that filter by it. /sync and sliding sync timelines keep the usual rules, as sticky events reach clients through their own section.

When a server joins a room, Zendrite sends it the sticky events that local users sent there and that are still sticky. Zendrite remembers these events in memory, so after a restart it only sends sticky events created since. Soft-failed sticky events are not re-evaluated when the room state changes.

State after the timeline

Section titled “State after the timeline”

A client that opts in to MSC4222 must not apply the state events of the timeline itself, so state_after holds them as well. An initial sync, a sync with full_state=true and a sync that newly joined a room send the room’s whole current state. An incremental sync sends the state changes between the since token and the end of the timeline, including those of a gappy (limited) timeline. For a room the user left, the state ends at their leave. state_after is sent even when it is empty, and the state filter applies to it. With lazy_load_members, it holds the memberships of the timeline senders, and an incremental sync keeps every membership change. Zendrite advertises org.matrix.msc4222 in unstable_features for clients that check it before opting in.

Bundled aggregations

Section titled “Bundled aggregations”

Zendrite adds unsigned.m.relations to events served by /messages, /context, /event, /relations, /search and /threads, and to /sync and sliding sync timelines that are limited. An unlimited timeline already carries every child event the client has not seen, so the client aggregates those itself. Each bundle holds the thread summary (m.thread), the most recent valid edit (m.replace) and the referencing events (m.reference). Only child events the requesting user may see are aggregated, and events from ignored users are left out. State events, and aggregations that arrive with events over federation, are never served with bundles.

Custom profile fields

Section titled “Custom profile fields”

GET, PUT and DELETE /_matrix/client/v3/profile/{userId}/{keyName} read, set and remove any profile field, and GET /_matrix/client/v3/profile/{userId} returns them all. The same endpoints are served under /_matrix/client/unstable/uk.tcpip.msc4133/, and /versions advertises uk.tcpip.msc4133 and uk.tcpip.msc4133.stable. /capabilities reports m.profile_fields (and uk.tcpip.msc4133.profile_fields) as enabled without restrictions, together with m.set_displayname and m.set_avatar_url.

A custom field name is a namespaced identifier such as org.example.job_title, at most 255 bytes long, and its value can be any JSON. A profile, including its display name and avatar URL, is limited to 64 KiB of canonical JSON; a change that would exceed this fails with M_PROFILE_TOO_LARGE. Only the display name and avatar URL are copied into membership events; deleting either one clears it. Guests may only change their display name. /_matrix/federation/v1/query/profile serves every field, also one at a time via field, and profiles of remote users include their custom fields. Deactivating an account removes its custom fields.

Jump to date

Section titled “Jump to date”

GET /_matrix/client/v1/rooms/{roomId}/timestamp_to_event returns the event closest to ts in the direction dir that the user may see. GET /_matrix/federation/v1/timestamp_to_event/{roomId} answers the same question for another server, from local events only. It returns the closest event the requesting server may see, checking at most 1000 events, and a server banned by the room’s ACL gets 403.

The local history of a room can have gaps, for example before the server joined it. Zendrite knows them from the backward extremities, the events whose prev_events it never fetched. When such a gap can hold an event closer to ts than the local result, and the user may see the event after the gap, the client endpoint asks up to five other servers in the room, those with the most joined members first. The first server that answers decides: if its event is closer, Zendrite backfills it with up to 20 events before it, so that /context and /messages can use it, and returns it when the user may see it. Otherwise, or when no server answers, the local result stands.

Delayed events

Section titled “Delayed events”

MSC4140 lets a client schedule an event for the server to send later, unless the client restarts or cancels the schedule first. Element Call uses it to end the call membership of a client that crashes or loses its connection; see MatrixRTC. Zendrite implements the unstable API that matrix-js-sdk and Synapse use:

  • The org.matrix.msc4140.delay query parameter, in milliseconds, on PUT /_matrix/client/v3/rooms/{roomId}/send/{eventType}/{txnId} and PUT /_matrix/client/v3/rooms/{roomId}/state/{eventType}/{stateKey} schedules the event and returns {"delay_id": ...} instead of an event ID.
  • PUT /_matrix/client/unstable/org.matrix.msc4140/rooms/{roomId}/delayed_event/{eventType}/{txnId} schedules an event from a body of delay_ms, content and an optional state_key.
  • POST /_matrix/client/unstable/org.matrix.msc4140/delayed_events/{delayId}/{cancel|restart|send}, and the older form POST .../delayed_events/{delayId} with {"action": ...}, manage a scheduled event. As in Synapse, these work without an access token, since the delay ID identifies the event; with one, they are rate-limited per device instead of per address.
  • GET /_matrix/client/unstable/org.matrix.msc4140/delayed_events/{delayId} returns one of the user’s delayed events, including a finalised object once it was sent, canceled or failed.
  • GET /_matrix/client/unstable/org.matrix.msc4140/delayed_events lists the user’s scheduled events, or with status=finalised the finalized ones, optionally only those named by delay_id parameters, with the field names of earlier revisions (delay, running_since) included as Synapse does. The list is not paginated, so from is ignored.

When scheduling, the event is built against the room’s current state, so a malformed event, or one the user may not send, is refused at once. A delay must be a positive integer; one above the maximum fails with 400 ORG.MATRIX.MSC4140_DELAY_TOO_LARGE, and a user with as many events scheduled as allowed gets 429 M_LIMIT_EXCEEDED with Retry-After set to when their next event is due. When delayed events are disabled, scheduling fails with 403 M_FORBIDDEN.

At its send time, the event is built from the room state at that moment and sent through the same path as a client’s send, including the authorization checks. A failure is recorded as the event’s finalised.error and is not retried. The send action differs: if sending fails, it returns the error and keeps the event scheduled. The sent event carries org.matrix.msc4140.delay_id in its unsigned data in the sender’s /sync, and no transaction_id. A message event scheduled with org.matrix.msc4354.sticky_duration_ms, through either scheduling endpoint, is sent as a sticky event, whose sticky period starts when it is sent. As for a direct send, the parameter is ignored for state events.

Retrying an action is safe: send succeeds for an event that was already sent, and cancel for one that was already canceled or failed. Other actions on a finalized event return 404 M_NOT_FOUND as in Synapse, rather than the 409 of the current MSC text, because matrix-js-sdk schedules a new delayed leave event when a restart finds none.

A user’s scheduled state event is canceled when another user changes the same state, and all of a user’s delayed events are deleted when the account is deactivated. Finalized events are kept for seven days, and at most 1000 per user.

Delayed events are stored in the user API database and sent by the process that serves clients. In HA deployments, that is the active process: a successor picks up the schedule from the database, and resends any event its predecessor was sending when it stopped. The resend uses the same roomserver transaction, keyed by the delay ID, so an event that did reach the room is not sent twice.

/versions advertises org.matrix.msc4140 while delayed events are enabled, and /capabilities reports the limits as org.matrix.msc4140.delayed_events, where a max_delay_ms of 0 means disabled.

Opt-in MSCs

Section titled “Opt-in MSCs”

The following MSCs are not enabled by default and must be activated in the mscs section of the config file:

mscs:
  mscs:
    - msc2836
    - msc2444
    - msc2753
    - msc3814
    - msc3861

MSC2836: Threading

Section titled “MSC2836: Threading”

The relationship index behind POST /_matrix/client/unstable/event_relationships is built from the roomserver output stream by the durable JetStream consumer MSC2836RoomServerConsumer. A relationship is therefore queryable shortly after its event is sent, not necessarily by the time the send request returns. A failed index write is retried until it succeeds, including by an HA successor, so a stored event never permanently loses its relationship. Disabling the MSC removes the consumer at the next start, except in HA mode, where it must be removed during the offline upgrade.

MSC2444 and MSC2753: Peeking

Section titled “MSC2444 and MSC2753: Peeking”

Peeking into a room whose ID names no server, as in room version 12, works locally when this server is in the room. Any other such room needs ?server_name= on POST /_matrix/client/v3/peek/{roomIdOrAlias} to peek over federation. Only world-readable, unencrypted rooms can be peeked, locally or by a remote server. Remote peeks ask to be renewed hourly; peeking again after the interval renews an expired outbound peek.

MSC3814: Dehydrated Devices v2

Section titled “MSC3814: Dehydrated Devices v2”

MSC3814 allows clients to store a “dehydrated” device on the server so that encrypted to-device messages (e.g. key shares) can be delivered while the user is offline. When the user signs in again, the client rehydrates the device and retrieves messages it missed.

What changes when MSC3814 is enabled:

  • PUT /_matrix/client/unstable/org.matrix.msc3814.v1/dehydrated_device — store a dehydrated device with its keys.
  • GET /_matrix/client/unstable/org.matrix.msc3814.v1/dehydrated_device — retrieve the current dehydrated device metadata.
  • DELETE /_matrix/client/unstable/org.matrix.msc3814.v1/dehydrated_device — remove the dehydrated device.
  • POST /_matrix/client/unstable/org.matrix.msc3814.v1/dehydrated_device/{deviceID}/events — retrieve to-device events addressed to the dehydrated device.

Configuration:

mscs:
  mscs:
    - msc3814

No additional configuration is needed beyond enabling the MSC.

MSC3861: OIDC Delegated Authentication

Section titled “MSC3861: OIDC Delegated Authentication”

MSC3861 delegates authentication to an external OpenID Connect (OIDC) provider such as Matrix Authentication Service (MAS). When enabled, Zendrite validates access tokens via OAuth 2.0 token introspection instead of managing passwords directly, and provisions accounts and devices on demand.

This changes the behaviour of a large part of the client-server API: password login and registration are disabled, session management moves to the provider, and clients without native OIDC support go through a legacy SSO compatibility layer.

Configuration:

mscs:
  mscs:
    - msc3861
  msc3861:
    issuer: "https://auth.example.com/"
    client_id: "0000000000000000000ZENDRITE"
    client_secret: "secret"

See Delegated authentication (OIDC) for the full setup guide, the complete configuration reference, client support, account provisioning rules, migration caveats and troubleshooting.
