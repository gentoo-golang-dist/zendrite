HA qualification report

This report is the release evidence for #352. It records the configuration, the measured recovery times, the defects the qualification found, and what it could not cover. Every number comes from the HA qualification harness; rerun it to reproduce them.

Configuration

Section titled “Configuration”
Setting Value
Code main at 0f0e02b5, which includes every fix listed under findings
Election timings the documented defaults: lease_duration 30s, renew_deadline 20s, retry_period 5s, ownership_timeout 45s
Recovery objective 120 s from fault to successful client and federation requests (ADR 0001)
Candidates 3, behind a router that checks the active-only endpoint every 500 ms, as the chart’s HAProxy does
PostgreSQL 17, primary with one synchronous standby, synchronous_commit=on, track_commit_timestamp=on
JetStream 3 nodes, file storage, sync_interval: always, replicas 3
Media S3 API (gofakes3, directory-backed)
Kubernetes kube-apiserver and etcd 1.37 from envtest, RBAC limited to Lease get, create, update
Federation a standalone homeserver joined to the test room
Client workload 5 messages/s with retried transaction IDs, long-poll /sync with existing tokens, to-device messages, read receipts, media upload and download, search, and 1 message/s from the remote server
Reference workload 100 users and 1,000 rooms with three members each, seeded before the scenario (ADR 0001)
Host one Linux container, amd64, 12 CPUs

Run with:

HACHAOS_CONTAINER=1 HACHAOS_TIER=full build/scripts/ha-qualification.sh
HACHAOS_CONTAINER=1 HACHAOS_TIER=reference HACHAOS_SCENARIOS=leader-sigkill,postgres-primary-failover,leader-partitioned-from-database build/scripts/ha-qualification.sh

Summary

Section titled “Summary”

Every scenario meets the safety contract and the recovery objective:

  • No acknowledged write was lost in any scenario, and every one reached /messages, a /sync client that kept its token across takeover, and the remote server.
  • The database audit found no overlap: in every scenario each generation’s commits all precede the next generation’s first commit.
  • No retired generation published to the broker, wrote media or sent federation after the bound its freshness window allows.
  • A resumed or partitioned former leader refused every direct write sent to it after its successor was promoted.
  • The router never saw two active candidates, and no status sample showed two candidates ready.
  • No event was stored twice, although a client retried a write across the fault in 14 of the 16 scenarios.
  • With the reference workload, a crashed leader is replaced and serving client and federation requests in 62.0 s.

Findings

Section titled “Findings”

The qualification found these defects; each is fixed in its own pull request, and every result above includes the fixes.

Defect Effect Fix
Receipt, send-to-device and signing-key consumers refused messages they had handled Every receipt and to-device message was sent to remote servers again every 30 s, and remote cross-signing keys were re-uploaded, forever #392
A JetStream publication whose broker died before acknowledging it waited on the caller’s context Client writes stalled for 30 s after losing the stream leader; an inbound federation transaction hung indefinitely and blocked the remote server’s queue #393
A destination queue loaded its backlog unordered, after events queued since the restart After a takeover, the remote server rejected all 53 queued events for missing prev_events #394
Backward pagination stepped over events that share a depth /messages and prev_batch skipped acknowledged messages whenever a late remote event forked the room at the same depth #395
A Lease holder partitioned from PostgreSQL kept renewing the Lease No standby could take over while the partition lasted; after the first fix, renewing through the drain still pushed takeover to 141.6 s with the reference workload #399
The sync and federation consumers panicked when a database write failed transiently With the reference workload, a 3 s PostgreSQL failover crashed the leader and became a 64 s leadership change #397
Transaction IDs were deduplicated only in a process-local cache If the old owner accepted a message into the room input stream but stopped before answering, the successor applied it and the client’s retry created a second event #404
The federation API consumed its streams before the roomserver was wired A successor that found a federation backlog crashed with a nil pointer on every promotion attempt; after a graceful shutdown, no candidate served for 2m50s #405
Missing-state resolution dropped the transaction’s origin while backing off from it After a takeover delivered events out of order, the remote server rejected 13 acknowledged messages instead of fetching the gap from the sender #406
A candidate took a free Lease without being able to reach PostgreSQL The restarted leader, still partitioned from the database, won the Lease back and held it through a failed 45 s fencing attempt, pushing takeover to 2m37s #407
A server woke its queue for a backing-off peer at most once a minute When that wakeup reached the successor before it was routable, the remote ignored its traffic for the rest of the minute and none of 118 remote messages arrived within 2 minutes #408

Two observations need no code change but affect operation:

  • The routing layer marks a backend down after one failed 500 ms check and closes its in-flight requests. A single slow probe under load did this once during setup; clients retried and succeeded, but a less aggressive fall would avoid it.
  • When the Kubernetes API or fencing is unavailable, no candidate serves, by design. Recovery then starts when the dependency returns, and the measured times include the fault’s duration.

Limitations

Section titled “Limitations”

The harness trades fidelity for reproducibility in a few places, so these still need exercising on real infrastructure:

  • Every process shares one host and one clock, and partitions are emulated by proxies, not by packet loss between machines.
  • The routing layer reimplements the chart’s HAProxy check rather than running HAProxy.
  • The S3 server is gofakes3, so S3 and shared-filesystem failover are not exercised.
  • The PostgreSQL operator is emulated: the harness promotes the standby, moves the service address, and relaxes synchronous commit while no standby exists.
  • Candidates restart one second after exiting, not with the kubelet’s crash-loop backoff.
  • Power loss, correlated storage failure and schema migrations between versions are out of scope; the upgrade scenario uses two builds of the same code.
  • Appservice and push deliveries are not verified end to end.
